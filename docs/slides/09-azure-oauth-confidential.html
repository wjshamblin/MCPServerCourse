Confidential Client

  • "Confidential" = the server can safely hold a secret
  • Azure gives you a client_secret value; server uses it to prove identity when exchanging the auth code for tokens
  • Suitable when the server-side deployment can keep a secret (env var, secrets manager, etc.)
  • Next step (09) moves to a public client with PKCE — useful when you can't safely ship a secret

Register the Azure App

  1. Portal → App registrations → New registration
  2. Platform: Web. Redirect URI:
    http://localhost:8000/callback
  3. Certificates & secrets → New client secret → copy the value (not the secret ID)
  4. Expose an API → accept default api://<client_id> → add scope access_as_user
  5. Copy tenant ID + client ID from Overview

The Whole Server


from fastmcp import FastMCP
from fastmcp.server.auth import OAuthProxy
from fastmcp.server.auth.providers.jwt import JWTVerifier

token_verifier = JWTVerifier(
    jwks_uri=f"https://login.microsoftonline.com/{TENANT}/discovery/v2.0/keys",
    issuer=f"https://login.microsoftonline.com/{TENANT}/v2.0",
    audience=CLIENT_ID,
)

scopes = [f"api://{CLIENT_ID}/access_as_user",
          "email", "openid", "profile", "offline_access"]

auth = OAuthProxy(
    upstream_authorization_endpoint=f"https://login.microsoftonline.com/{TENANT}/oauth2/v2.0/authorize",
    upstream_token_endpoint         =f"https://login.microsoftonline.com/{TENANT}/oauth2/v2.0/token",
    upstream_client_id     =CLIENT_ID,
    upstream_client_secret =CLIENT_SECRET,
    valid_scopes           =scopes,
    extra_authorize_params ={"scope": " ".join(scopes)},
    token_verifier         =token_verifier,
    base_url               =SERVER_BASE_URL,
)

mcp = FastMCP("AzureConfidentialDemo", auth=auth)

FastMCP 3.x API Note

  • Earlier drafts of this course used upstream_scopes=...
  • FastMCP 3.x renamed it to valid_scopes=... and moved the outbound scope list to extra_authorize_params
  • Net effect is the same: Azure sees the scopes in the authorize request, FastMCP validates them in the incoming tokens

Azure JWT ≠ Duke Opaque

  • Azure AD issues a JWT access token whose header references a key ID
  • Validation is purely local: fetch JWKS once, verify signature + issuer + audience + exp
  • No per-call network hop to Azure — cheaper and faster than Duke introspection
  • Scopes travel in the scp (delegated) or roles (app) claim

Tools & Resources


@mcp.tool
def hello(name: str = "world") -> str:
    return f"hello, {name}!"

@mcp.tool
def whoami() -> dict:
    tok = get_access_token()
    if tok is None:
        return {"error": "no access token in context"}
    keep = ("oid", "upn", "preferred_username",
            "name", "tid", "scp", "appid")
    return {
        "client_id": tok.client_id,
        "scopes":    tok.scopes,
        "claims":    {k: tok.claims.get(k) for k in keep
                      if tok.claims.get(k)},
    }

@mcp.resource("user://me")
def me() -> dict:
    return whoami()

Azure Claim Cheat Sheet

ClaimMeaning
oidStable user object ID (the one to index on)
upn / preferred_usernameUser's email-shaped principal name
nameDisplay name
tidTenant ID — useful for multi-tenant apps
scpSpace-separated granted delegated scopes
rolesApp roles (when using app-only grants)
appidThe client that obtained the token

Key Takeaways

  • Azure AD uses OAuthProxy + JWTVerifier
  • Confidential client = server holds the secret, exchanges code for tokens
  • JWT validation is local (JWKS) — no per-call introspection
  • FastMCP 3.x: valid_scopes + extra_authorize_params["scope"]
  • Same minimal file shape as step 08 — only the auth block changes
