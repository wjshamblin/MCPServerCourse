Step 03

Context, Logging, and Elicitation

Your tools' connection back to the client

So far our tools have been simple functions that take input and return output. Now we add bidirectional communication: your tools can log messages, report progress, and even ask the user questions mid-execution.

The Context Object

Gateway to MCP features inside your tools

  • Auto-injected via ctx: Context parameter
  • Hidden from the tool schema (LLM never sees it)
  • Requires async def (all Context methods are async)
The Context object is how your tool communicates with the MCP client during execution. You simply add a ctx: Context parameter to your function and FastMCP injects it automatically. The LLM never sees this parameter in the tool schema.

Context Injection


from fastmcp import Context, FastMCP

@mcp.tool
async def my_tool(query: str, ctx: Context) -> str:
    # ctx is injected automatically
    # LLM only sees: {"query": "string"}
    await ctx.info("Working on it...")
    return "done"
  • ctx is stripped from the JSON schema
  • Function must be async def
  • Works with tools, not resources or prompts
Here is the pattern. Add ctx: Context as a parameter. FastMCP sees the Context type annotation and knows to inject the object at call time, removing it from the schema. The LLM only sees the query parameter. Note the function must be async because all context methods are awaitable.

Logging to the Client

MethodWhen to use
ctx.debug(msg)Verbose diagnostic info
ctx.info(msg)Status updates
ctx.warning(msg)Something unexpected
ctx.error(msg)Something failed

These go to the client, not to your server logs.

These logging methods send messages back to the MCP client during tool execution. The client can display them to the user or in a debug panel. This is different from Python's logging module, which writes to your server logs. Context logging is for the user to see.

Progress Reporting


@mcp.tool
async def analyze_text(text: str, ctx: Context) -> str:
    await ctx.info("Starting text analysis...")
    await ctx.report_progress(progress=1, total=4)
    words = text.split()
    await ctx.report_progress(progress=2, total=4)
    # ... compute frequencies ...
    await ctx.report_progress(progress=3, total=4)
    sentences = len([s for s in text.split(".") if s.strip()])
    await ctx.report_progress(progress=4, total=4)
    await ctx.info("Analysis complete")
    return json.dumps({"word_count": len(words), ...})

Clients can display a progress bar based on progress / total.

Progress reporting lets the client show the user how far along a long-running operation is. You call report_progress with the current step and the total number of steps. The client can render this as a progress bar. Combine it with info logging for detailed status updates.

Elicitation: Interactive Input

  • Tool can pause and ask the user a question
  • User responds through the MCP client
  • Three possible outcomes: accept, decline, cancel
  • Powerful for confirmations and multi-step workflows
Elicitation is one of the most powerful MCP features. Your tool can pause mid-execution and ask the user a question. The MCP client presents the question to the user, collects their response, and sends it back to your tool. This enables confirmation dialogs, multi-step wizards, and interactive workflows.

Elicitation in Code


@mcp.tool
async def delete_records(table: str, confirm: bool = False,
                         ctx: Context = None) -> str:
    if not confirm:
        result = await ctx.elicit(
            message=f"Delete all records from '{table}'?",
            response_type=bool,
        )
        if result.action != "accept" or not result.data:
            return "Operation cancelled."
    await ctx.warning(f"Simulating delete from '{table}'")
    return f"(Simulated) Deleted all records from '{table}'."
Here is a real example from the codebase. The delete_records tool asks the user for confirmation before proceeding. The elicit call pauses the tool, sends the question to the client, and waits for the user's response. The response_type tells the client what kind of input to collect.

Elicitation Response Handling


result = await ctx.elicit(
    "Are you sure?",
    response_type=bool,
)

if result.action == "accept":
    # User said yes
    data = result.data  # the actual value (True/False)
elif result.action == "decline":
    # User said no
    ...
elif result.action == "cancel":
    # User cancelled the dialog
    ...
  • action — what the user did (accept/decline/cancel)
  • data — the typed value the user provided
  • response_type can be bool, str, or a Pydantic model
The elicitation result has two key fields. Action tells you what the user did: accept means they provided a response, decline means they said no, cancel means they dismissed the dialog. Data contains the actual typed value. You can use bool for yes/no, str for text input, or even a Pydantic model for structured input.

Other Context Capabilities

  • ctx.read_resource(uri) — read a resource from within a tool
  • ctx.sample(prompt) — ask the client's LLM to generate text
  • ctx.request_id — unique ID for this request
  • ctx.session_id — the MCP session ID
The Context object has several other capabilities. read_resource lets a tool read one of the server's own resources. sample asks the client's LLM to generate text, which is useful for sub-tasks. request_id and session_id give you identifiers for tracing and debugging.

Key Takeaways

  • Context = your tool's connection to the MCP client
  • Logging levels: debug, info, warning, error
  • Progress: report_progress(progress, total)
  • Elicitation: pause and ask the user questions
  • Always use async def with Context
