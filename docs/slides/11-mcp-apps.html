MCP Apps — Interactive UIs

Three hand-built apps + one Generative UI provider, in one file

What Is an MCP App?

  • An interactive UI panel that renders inside the AI client (Claude Desktop, Cursor, VS Code Copilot)
  • Declared server-side, rendered client-side
  • Buttons / inputs fire actions that round-trip back to your MCP server as tool calls
  • The same tools the App uses are also callable by the LLM directly

Think "renderable tool surface" rather than "web app".

📚 gofastmcp.com/apps/overview

What This Branch Ships

  • Counter — minimal end-to-end example
  • Progress — Loader / Ring / Progress driven by a real 4-stage server chain
  • Deploy Console — stat cards, Dialog, server-side elicitation
  • Generative UI — LLM writes Prefab code at runtime in Pyodide
  • Plain tools: hello, add, render_report (progress streaming), get_lab_spending (seed data)

Auth + database stripped — explicit auth = None. Drop in a step-07..10 auth block to gate everything.

The Four-Step Pattern

  1. Create a FastMCPApp — it bundles UI + backing tools
  2. Decorate each backing function with @app.tool(model=True) so it's callable from the UI and from the LLM directly
  3. Decorate the UI entry point with @app.ui(); return a PrefabApp layout built from prefab_ui.components
  4. Register on the main server: mcp.add_provider(app)

Counter App — Backing Tools


_state: dict[str, int] = {"count": 0}   # demo-only; in-memory
counter_app = FastMCPApp("Counter")

@counter_app.tool(model=True)
def get_counter() -> dict:
    return {"count": _state["count"]}

@counter_app.tool(model=True)
def bump_counter(by: int = 1) -> dict:
    _state["count"] += by
    return {"count": _state["count"], "delta": by}

@counter_app.tool(model=True)
def reset_counter() -> dict:
    _state["count"] = 0
    return {"count": 0}

model=True = the LLM can also call these. The UI will call them via CallTool(...).

Counter App — UI


@counter_app.ui()
async def counter_view() -> PrefabApp:
    with Column(gap=4, css_class="p-6") as view:
        Heading("Counter", level=2)
        Text("A shared in-memory counter. Click a button (or just ask "
             "the model to bump it) and watch the value update.",
             css_class="text-gray-400 text-sm")
        Separator()
        with Row(gap=8, css_class="items-center"):
            Metric(label="Count", value=Rx("count"))
        with Row(gap=2):
            Button("Refresh",
                on_click=CallTool(get_counter,
                    on_success=[SetState("count", RESULT["count"])]))
            Button("+1",
                on_click=CallTool(bump_counter, arguments={"by": 1},
                    on_success=[
                        SetState("count", RESULT["count"]),
                        ShowToast("+1", variant="success")]))
            # +10 and Reset elided for space
    return view

mcp.add_provider(counter_app)

Reactive State Cheat Sheet

HelperMeaning
STATERoot of the client-side reactive store
Rx("count")Bind a component value to STATE.count
RESULTThe tool-call return payload, inside on_success

ShowToast("...", variant=...)Fire a user-visible toast

Models and Apps Coexist

  • Because model=True, the LLM can say "bump the counter by 5" and bump_counter runs the same way a button click would
  • UI and LLM share state: click +1, then ask the model for the value → it sees 1
  • This is the superpower of MCP Apps — humans and models share the surface

Progress — Real Server-Driven Stages

  • Clicking Render Report fires four CallTools in sequence
  • Built programmatically so nesting reads left-to-right — no pyramid-of-doom
  • Each stage is a real server round-trip; the percent you see is the server's answer

def _build_stage_chain(stages):
    if not stages:
        return [SetState("running", False), ShowToast("Done")]
    head, *tail = stages
    return [CallTool(render_stage, arguments={"stage": head},
                     on_success=[SetState("percent", RESULT["percent"]),
                                 *_build_stage_chain(tail)])]

Companion plain tool: render_report uses ctx.report_progress() for clients with native progress UI.

Deploy — Server-Side ctx.elicit()

  • The Rollback button fires a tool that pauses and asks the client for typed input
  • The confirmation UI is rendered by the MCP client, not by Prefab
  • Elicitation is a protocol feature, not a UI gadget — works across all MCP clients

class RollbackConfirmation(BaseModel):
    confirm: bool = Field(default=False, description="Confirm rollback")
    reason: str   = Field(default="", max_length=200)

async def rollback_service(service: str, ctx: Context) -> dict:
    result = await ctx.elicit(
        message=f"Roll {service} back?",
        response_type=RollbackConfirmation,
    )
    if not isinstance(result, AcceptedElicitation) or not result.data.confirm:
        return {"ok": False, "reason": "not confirmed"}

Generative UI — The LLM Writes the UI

  • The three apps above are hand-built: you write the Prefab code server-side
  • Generative UI flips that: the LLM writes Prefab Python at runtime, in a Pyodide sandbox
  • Code streams into the client token by token — the user watches the UI build up

📚 gofastmcp.com/apps/generative

One Line to Register


from fastmcp.apps.generative import GenerativeUI

mcp.add_provider(GenerativeUI())

That one line exposes two tools:

  • generate_prefab_ui(code, data=?) — executes Prefab code in Pyodide and renders the result. Streams partial code browser-side as the LLM types.
  • search_prefab_components(query) — lets the LLM discover components before writing code

Key Takeaways

  • An MCP App = UI + tools that round-trip through MCP
  • One file can ship many Apps via mcp.add_provider(app)
  • model=True tools are reachable from both the UI and the LLM — use that
  • Prefab UI state is reactive: Rx reads, SetState writes, RESULT is what the tool returned
  • Elicitation (ctx.elicit) is a protocol feature — confirmation UI comes from the client, not Prefab
  • Generative UI lets the LLM build dashboards on the fly — hand-built and generated apps coexist in one server
