Step 07

Lifespans, Tasks, and Composition

Production patterns for MCP servers

Production Patterns

  • Lifespans — Server-level setup/teardown
    (database connections, external clients)
  • Background Tasks — Long-running operations that don't block
    (large exports, batch processing)
  • Composition — Combine multiple servers into one endpoint
    (financial + directory + analytics)

Per-Request Connections

In Steps 05–06, every tool call opens a new SQLite connection:

  • Connection overhead on every request
  • No connection reuse or pooling
  • What if the database isn't available at startup?
  • No clean shutdown/cleanup

What we want: open once at startup, close on shutdown

Lifespans: The Solution


from fastmcp.server.lifespan import lifespan

@lifespan
async def db_lifespan(server):
    db = DatabasePool(config.database_path_resolved)
    await db.connect()
    try:
        yield {"db": db}    # this dict is the lifespan context
    finally:
        await db.close()    # guaranteed cleanup

mcp = FastMCP("Server", lifespan=db_lifespan)
  • Code before yield runs at startup
  • Code after yield runs at shutdown
  • The yielded dict is available to all tools via ctx

Using Lifespan Context


def get_db(ctx: Context) -> DatabasePool:
    return ctx.lifespan_context["db"]

@mcp.tool
async def query_sql(sql: str, ctx: Context) -> str:
    db = get_db(ctx)
    rows, total = await db.execute_query(sql)
    return json.dumps({
        "total_rows": total,
        "returned_rows": len(rows), "data": rows,
    })

Every tool gets the same database connection — no per-request overhead

DatabasePool

Persistent connection manager


class DatabasePool:
    def __init__(self, db_path: Path):
        self.db_path = db_path
        self._conn: aiosqlite.Connection | None = None

    async def connect(self) -> None:
        self._conn = await aiosqlite.connect(str(self.db_path))
        self._conn.row_factory = aiosqlite.Row

    async def close(self) -> None:
        if self._conn: await self._conn.close()

Background Tasks: The Problem

  • Some operations take a long time (large CSV exports)
  • Blocking the client during a 30-second export = bad UX
  • MCP tools are synchronous request/response by default


Solution: run as a background task — client gets a task ID immediately

Background Tasks: The Solution


@mcp.tool(task=True)
async def export_report(query_description: str,
                        sql: str, ctx: Context) -> str:
    db = get_db(ctx)
    await ctx.info(f"Starting report: {query_description}")
    rows, total = await db.execute_query(sql, max_rows=50_000)
    output = io.StringIO()
    writer = csv.DictWriter(output, fieldnames=rows[0].keys())
    writer.writeheader()
    writer.writerows(rows)
    return json.dumps({"csv": output.getvalue()})
  • task=True is the only change needed
  • Requires pip install "fastmcp[tasks]"
  • Must be async def

Server Composition: The Problem

  • You have multiple servers (financial, directory, analytics...)
  • Running them on separate ports is awkward for clients
  • Clients need to connect to multiple endpoints
  • Tool names may collide across servers


Solution: mount them under one server with namespaces

Server Composition: The Solution


from fastmcp import FastMCP
from financial_server import mcp as financial_mcp

main = FastMCP(
    "UniversityServices",
    instructions="Unified university services server. "
                 "Use finance_* tools for financial data.",
)

main.mount(financial_mcp, namespace="finance")
# Tools become: finance_query_sql, finance_ask, etc.
  • namespace prefix prevents naming collisions
  • Resources get prefixed too
  • Dynamic: add tools to child server → immediately visible through parent

Key Takeaways

  • Lifespans: setup/teardown with the yield pattern
  • Background tasks: task=True for long operations
  • Composition: mount() to combine servers


These patterns make MCP servers production-ready
