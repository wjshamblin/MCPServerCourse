Step 10

Directory Server with On-Behalf-Of

Reaching Microsoft Graph as the calling user

Why This Branch Grows

  • Steps 07 – 09 were intentionally tiny (one file, one idea)
  • Step 10 keeps the same auth shape but now does something substantive: call Microsoft Graph on the user's behalf
  • That needs real code, so server.py pulls in three supporting modules
  • All composition-with-financial-server framing is gone — server.py is the directory server
  • We build on FastMCP's AzureProvider + EntraOBOToken rather than hand-rolling the exchange

Upstream reference: FastMCP — Azure OBO guide

The Problem OBO Solves

The user's MCP token is scoped for our API:

aud = api://<our client id>/access_as_user

Graph won't accept that token — it wants its own audience:

aud = https://graph.microsoft.com
  • App-only creds would work, but then every user gets the union of Graph permissions our app was granted
  • OBO exchanges the user's MCP token for a Graph token with the user's identity preserved

OBO Flow

User → MCP client → Our server
                      │
                      │ POST /token (jwt-bearer grant)
                      │   assertion = user's MCP token
                      │   scope     = Graph scopes
                      │   client_id + client_secret (confidential!)
                      ▼
                   Azure AD
                      │
                      │ New access_token (aud=graph.microsoft.com)
                      │ preserves oid/upn of user
                      ▼
                   Our server ──────── GET /users?...  ──────▶ Graph
                                                               │
                                       ◀────── user results ───┘

Grant type: urn:ietf:params:oauth:grant-type:jwt-bearer + requested_token_use=on_behalf_of.

Why Confidential Again?

  • OBO requires the downstream call to /token be authenticated
  • Public clients can't do that — they have no secret
  • So step 10 backs off to a confidential client (secret in the server's env)
  • Step 09's security add-ons (allowlist, audit) still apply in principle; this branch keeps focus on OBO, so they're not re-added here

Azure App Setup

  1. App registration as in step 08: Web platform, redirect URI http://localhost:8000/auth/callback, client secret
  2. Manifest → "requestedAccessTokenVersion": 2 (AzureProvider speaks v2)
  3. Expose an API → keep access_as_user
  4. API permissions → Microsoft Graph → Delegated:
    • User.Read.All
    • Directory.Read.All
  5. Grant admin consent on those scopes — required or OBO fails with AADSTS65001

Auth + OBO Wiring


from fastmcp.server.auth.providers.azure import (
    AzureProvider, EntraOBOToken,
)

auth = AzureProvider(
    client_id=AZURE_CLIENT_ID,
    client_secret=AZURE_CLIENT_SECRET,       # OBO needs the secret
    tenant_id=AZURE_TENANT_ID,
    required_scopes=["access_as_user"],      # our API scope
    additional_authorize_scopes=[            # pre-consented, enables OBO
        "openid", "profile", "email",
        "https://graph.microsoft.com/User.Read.All",
        "https://graph.microsoft.com/Directory.Read.All",
    ],
    base_url=SERVER_BASE_URL,
)

graph     = GraphClient(GRAPH_BASE_URL)
directory = DirectoryService(graph=graph)    # no OBO in constructor

Graph scopes ride along in additional_authorize_scopes so Azure consents them up-front. OBO can only exchange for scopes the user has already consented to.

EntraOBOToken as a Parameter Default

async def find_user(
    query: str,
    graph_token: str = EntraOBOToken(GRAPH_SCOPES),
) -> str:
    results = await directory.find_user(graph_token, query)
    ...
  • EntraOBOToken(scopes) is a FastMCP dependency, not a real default
  • Per request it grabs the inbound user token and exchanges it for a Graph token scoped to scopes
  • Backed by azure.identity.aio.OnBehalfOfCredential — built-in caching keyed on (assertion, scopes)
  • Tool receives a ready-to-use token; OBO mechanics never leak into the MCP schema

DirectoryService


class DirectoryService:
    """Thin coordinator for Microsoft Graph directory calls."""

    def __init__(self, graph: GraphClient):
        self.graph = graph

    async def find_user(self, graph_token: str, query: str):
        logger.info(f"Finding user: {sanitize_for_log(query)}")
        return await self.graph.find_user(graph_token, query)

    async def get_user_groups(self, graph_token: str, user_id: str):
        logger.info(f"Getting groups for: {sanitize_for_log(user_id)}")
        return await self.graph.get_user_groups(graph_token, user_id)

OBO is gone from this layer entirely; it just takes an already-exchanged Graph token.

async def find_user(
    query: str,
    graph_token: str = EntraOBOToken(GRAPH_SCOPES),

    results = await directory.find_user(graph_token, query)
    users = [UserResult.from_graph(r).model_dump() for r in results]

Key Takeaways

  • OBO lets a server call downstream APIs as the user, not as the app
  • Requires a confidential client — the secret is part of the exchange
  • AzureProvider + EntraOBOToken collapse ~100 lines of hand-rolled plumbing to a single parameter default
  • Downstream scopes must be in additional_authorize_scopes so they're consented at login
  • Preserves audit, least-privilege, and user identity across the network hop
