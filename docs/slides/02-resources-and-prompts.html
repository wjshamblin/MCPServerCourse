Step 02: Resources and Prompts

Adding read-only data and reusable templates

In step 01 we built tools. Now we complete the picture with the other two MCP primitives: resources and prompts. Resources let you expose data, and prompts give you reusable message templates.

The Three MCP Primitives

PrimitivePurposeExample
ToolsActions the LLM can performExecute a query, send email
ResourcesRead-only data for the LLMConfig files, database schema
PromptsReusable message templatesCode review template
These three primitives are the foundation of MCP. Tools perform actions. Resources expose data. Prompts provide reusable templates. Together they give an LLM everything it needs to work with your systems.

Resources: What Are They?

  • Read-only data exposed via URI
  • LLM clients can discover and read them
  • Think of them as "files" the AI can access
  • No side effects (unlike tools)
Resources are the simplest primitive. They are read-only, meaning the LLM can read them but cannot modify them. Each resource has a URI that identifies it. The client can list all available resources and read any of them.

Static Resource


@mcp.resource("resource://about", mime_type="text/plain")
def get_about() -> str:
    """Static information about this server."""
    return (
        "HelloWorld MCP Server v0.2\n"
        "A demo server for learning MCP concepts.\n"
        "Available: tools (echo, add, greet), resources, and prompts."
    )
  • URI: resource://about
  • mime_type tells the client what format to expect
  • Returns the same content every time
This is the simplest kind of resource. It has a fixed URI and returns the same string every time. The mime_type helps the client understand the format. Think of it as a static file the LLM can read.

Dynamic Resource


@mcp.resource("resource://server-time", mime_type="application/json")
def get_server_time() -> str:
    """Dynamic resource that returns the current server time."""
    now = datetime.now(timezone.utc)
    return json.dumps({
        "utc": now.isoformat(),
        "unix_timestamp": int(now.timestamp()),
    })

Runs fresh each time the client reads it.

Dynamic resources look the same as static ones in code, but the function computes a new result each time. Here we return the current server time. The LLM gets fresh data every time it reads this resource.

Resource Templates


@mcp.resource("resource://greeting/{name}", mime_type="text/plain")
def get_greeting_resource(name: str) -> str:
    """Resource template — personalized greeting for any name."""
    return f"Hello, {name}! This greeting was generated "
           f"from a resource template."
  • URI parameters use {name} syntax (RFC 6570)
  • Parameters map to function arguments
  • One template → infinite resources
Resource templates let you create parameterized URIs. The curly brace syntax follows RFC 6570 URI templates. The client can fill in the parameter to read different resources from the same template. This is powerful for things like user profiles, database records, etc.

Resources vs Tools

Resources

  • Read-only
  • URI-addressed
  • For exposing data
  • No side effects

Tools

  • Can have side effects
  • Function-call style
  • For performing actions
  • LLM decides when to call

Rule of thumb: If it just returns data → resource. If it does something → tool.

The key distinction is side effects. Resources are safe to read at any time. Tools might change state, send emails, delete records, etc. If you are unsure, ask: does this function change anything? If no, make it a resource. If yes, make it a tool.

Prompts: What Are They?

  • Reusable message templates
  • NOT system prompts — they're templates a client requests
  • Parameterized with typed arguments
  • Can return single messages or conversations
Prompts are often misunderstood. They are NOT system prompts injected into every request. Instead, they are templates that a client can explicitly request. The client picks a prompt, fills in the parameters, and gets back formatted messages to use in a conversation.

Simple Prompt


@mcp.prompt
def summarize(text: str, style: str = "concise") -> str:
    """Generate a summarization request with a specified style."""
    return f"Please provide a {style} summary of the following "
           f"text:\n\n{text}"
  • Returns a plain string → becomes a user message
  • Default values make parameters optional
  • Client discovers available prompts and their parameters
The simplest prompt returns a string. FastMCP wraps it in a user message automatically. The style parameter has a default, so the client can omit it. This gives you a reusable template for summarization requests.

Multi-message Prompt


from fastmcp.prompts import Message

@mcp.prompt
def code_review(language: str, code: str) -> list[Message]:
    return [
        Message(f"Review this {language} code:\n\n```{language}\n{code}\n```"),
    ]

@mcp.prompt
def explain_concept(concept: str, audience: str = "beginner") -> list[Message]:
    return [
        Message(f"Explain '{concept}' to a {audience} audience."),
        Message("I'll explain this step by step.", role="assistant"),
    ]
For more complex prompts, return a list of Message objects. Each message has content and an optional role. The explain_concept prompt includes an assistant preamble, which seeds the conversation with a specific tone. This is useful for setting up multi-turn interactions.

Key Decorator Arguments

ArgumentPurpose
uri / nameIdentifier for the resource or prompt
mime_typeContent format (resources only)
descriptionCustom description override
tagsCategorization metadata
These are the most common arguments you will pass to the resource and prompt decorators. The URI or name identifies the item. Mime type tells the client what format to expect. Description overrides the docstring if you need a different public-facing description. Tags help with organization.

Key Takeaways

  • Resources = read-only data via URI
  • Resource templates = parameterized URIs
  • Prompts = reusable message templates
  • Together with tools, these are the three MCP primitives
